> **Source-of-truth implementation specification** for Nextcode feature-parity work.
> Generated by deep source-level research across nextcode + 25 reference coding-agent repositories.
> An implementer may select a feature ID, inspect the cited source, understand current/reference/target behavior, implement, and test — without repeating the research.

**Status:** Research complete. §10 contains full 28-section specs for all 15 P0/P1 features. Audit (real-world verification) done — see `NEXTCODE-EXISTING-FEATURE-AUDIT.md`.
**Branch basis:** `review` (HEAD 351ee19f4).

## 1. Executive Summary

### How complete is Nextcode today?

Nextcode is a **large, mature monorepo** (~100 crates, 117 under `crates/`). The **Face TUI** (`crates/xai-grok-pager/`) is a **superset fork of Grok Build's Face UI** — it already ships an unusually rich set of differentiators: which-key overlay (Ctrl+K), timeline rail, sticky scrollback headers, a 10-segment configurable statusline, mouse text-selection + scrollbar drag, a toast stack, session foreign-import, cloud session sync, MCP trust+OAuth, a plugin marketplace, ambient/overnight autonomous runs, and Best-of-N masonry. The **CLI/core** (`src/cli/`, `next-code-app-core`, `next-code-base`) is deep: multi-provider routing, ACP serving, sessions, subagents/teams/swarm, permission modes, compact/context, diff review, and more.

### Strongest areas

- **TUI differentiators** — which-key, timeline rail, sticky headers, statusline config, mouse support, toasts.
- **Provider/agent core** — multi-provider with failover, ACP, sessions, subagents/teams/swarm, Best-of-N, compaction with retries, permission modes, cloud-session + foreign-session import.
- **Safety foundation** — DCG (decision-correctness gate), bash-destructive gate, trust + OAuth for MCP.

### Weakest areas (confirmed gaps)

- **No command-risk justification** (P0): permission decisions don't explain *which rule matched and why*.
- **No multi-tier compaction** (P0): only reactive context-limit compaction; no proactive/semantic/preemptive tiers.
- **No keybinding validation/collision detection** (P1): user `keybindings.json` remaps can silently conflict.
- **No full vim input engine** (P1): `xai-ratatui-textarea` has vim+readline but no registers/text-objects.
- **No streaming table holdback** (P1): markdown tables are committed as-streamed; no live reflow.
- **No folder-trust startup dialog** (P1), **no append-only audit log** (P1), **no shell completion** (P1), **no Esc-Esc backtrack** (P1), **no agentic cross-project session search** (P1), **no parallel tool scheduler** (P1).

### What should become the foundation

- **Nextcode Face TUI (`xai-grok-pager`) = the TUI foundation.** It is already the Grok Build TUI plus nextcode extensions. Keep and extend it.
- **Nextcode CLI/core = the logic foundation.** Multi-provider routing, sessions, permission engine, agent loop.
- **jcode** supplies upstream compaction modes, command-risk crate, and stream pacer (already byte-identical in `next-code-tui`).
- **grok-build** supplies the external-editor compose flow and shell completion (both trivial COPY since Face is a fork of grok-build).

### What should be ported (priority set)

See the master matrix (§7) and the ranked Top-15 (§8). Highest-impact ports: command-risk + justification (P0), multi-tier compaction (P0), permission decision debug (P1), keybinding validation (P1), vim engine (P1), table holdback (P1), Esc-Esc backtrack (P1), cross-project session search (P1), parallel tool scheduler (P1), folder-trust dialog (P1), audit log (P1), shell completion (P1), external-editor compose (P1).

### What should NOT be ported

Ambient pets / screen-reader layout / i18n / SDK control plane are marked **DO_NOT_PORT or DEFERRED** in this phase (P3, cross-language REIMPLEMENT with poor cost/benefit vs current priorities). Several nextcode differentiators are **DO_NOT_PORT** explicitly so they are not regressed (which-key, timeline, sticky headers, statusline config, toast stack, Best-of-N, team roster, MCP modal, marketplace).

## 2. Goals

1. Reach **full relevant feature coverage** from all reference repositories.
2. Port the **best UI/UX/DX** for each capability, not the first implementation found.
3. **Improve nextcode core logic** where a reference is demonstrably better.
4. Treat **TUI and CLI as first-class product surfaces**.
5. Preserve nextcode's Rust-native quality and core architecture.
6. Batch work by shared Rust modules to **minimize rebuild cost**.

## 3. Non-goals

- No mobile/desktop.
- No blind feature copying.
- No rewrite of the core provider/agent loop unless a defect demands it.
- No cosmetic-only churn in already-parity areas.

## 4. Nextcode Architecture (map)

### 4.1 Repository layout

```
src/                          → binary entrypoint + CLI (args, login, provider_init, startup, commands/)
crates/next-code-app-core/    → agent loop, tools, server (comm), ambient/overnight, execution policy
crates/next-code-base/        → auth, providers, usage, config, sessions, todos, storage
crates/next-code-provider-*/  → per-provider runtimes (openai, anthropic, openrouter, gemini, grok-runtime, ...)
crates/next-code-message-types → Message, StreamEvent, ContentBlock, ToolDefinition
crates/xai-grok-pager/        → Face TUI (primary) — fork of grok-build Face
crates/xai-grok-pager-render/ → rendering primitives
crates/xai-grok-shared/       → shared TUI state (status_line, clipboard, settings)
crates/xai-grok-shell/, xai-grok-agent/, xai-acp-lib/ → grok shell/agent/ACP protocol
crates/next-code-tui/         → legacy TUI (jcode fork, being retired)
```

### 4.2 TUI architecture (Face)

- Modules: `acp` (session protocol), `actions` (keybindings → actions), `app` (App state machine, event loop, dispatch), `diff`, `input`, `models`, `notifications`, `scrollback` (rendering, sticky headers), `settings`, `slash` (slash commands), `views` (modals, palette, which-key, toasts, timeline, statusline, tasks pane, agent panel, subagent catalog, MCP modal, permission view).
- Event/state: `App` holds the whole view state; `event_loop.rs` dispatches; `dispatch/` routes to handlers; actions mutate state then re-render.
- Keybindings: `actions/user_bindings.rs` loads `keybindings.json`; `actions/mod.rs` registers defaults.

### 4.3 CLI + core architecture

- Entry `src/main.rs` → `src/lib.rs` → `src/cli/` (clap-based args, subcommands).
- Agent loop: `next-code-app-core/src/agent/` (turn_loops, turn_streaming_mpsc, turn_execution, provider, compaction, best_of_n_orchestrator).
- Provider trait: `next-code-provider-core/src/lib.rs` `Provider` (complete, complete_split, model_routes, set_model, fork, ...).
- Sessions: `next-code-base/src/session/` + `session.rs`; storage under `next-code-base/src/storage.rs`.
- Permissions: `next-code-base/src/safety.rs` (AUTO_ALLOWED:183, ActionLog), `next-code-app-core/src/dcg_bridge.rs`, `src/face_permission.rs`.
- Config: `next-code-base/src/config*`, `config_file.rs`; env `NEXT_CODE_*`.

## 6. Research Methodology

- Read actual source for every claimed feature (no README trust).
- Traced `input → keybinding → state → agent/runtime → render → output` for high-value features.
- Compared implementations across repos and selected the best source per feature.
- Classified every finding (see §7) and assigned priority/risk/build-cost/strategy.

### 10.1 NX-PERM-002 — Command-risk classifier + justification

**STATUS**
- Current: PARTIAL · Priority: P0 · Category: UI / UX / DX / Logic
- Strategy: PORT · Best source: jcode (`jcode-command-risk`) + CodeWhale (`command_safety.rs`) + hermes (`approval.py`)
- Nextcode target files: new `crates/next-code-command-risk/`; `crates/next-code-base/src/safety.rs`; `crates/next-code-app-core/src/dcg_bridge.rs`; `src/face_permission.rs`

**1. WHY**
Every permission allow/deny today is opaque: the user (or the model) is told *whether* an action is allowed, never *why*. A command-risk classifier that returns a RiskLevel + Justification per command converts permission friction into trust, matches the safety posture of the strongest reference agents, and is the prerequisite for NX-PERM-001 (decision debug).

**2. CURRENT NEXTCODE BEHAVIOR**
`crates/next-code-base/src/safety.rs` has `AUTO_ALLOWED:183` (a hardcoded allowlist) plus a bash-destructive gate. `crates/next-code-app-core/src/dcg_bridge.rs` runs the DCG (decision-correctness gate) classify path. `src/face_permission.rs` surfaces the allow/deny decision to Face. None of these produce a per-command `RiskLevel` or a human-readable `Justification`. The user sees "allowed" or "denied" with no reason.

**3. EXACT CURRENT CODE PATH**
- `safety.rs:183` `AUTO_ALLOWED` — the static allow set.
- `safety.rs` — `classify_*` / `is_*` destructive gates (bash-specific).
- `dcg_bridge.rs` — `classify_for_session`, `BridgeDecision::Prompt/AutoAllow/AutoDeny`.
- `face_permission.rs` — decision → Face permission_view.

**4. REFERENCE IMPLEMENTATION**
- jcode `crates/jcode-command-risk/` (`.tmp/jcode`, branch `origin/fix/openai-quota-window-dedup`, commit `659b8cc15`): files `src/lib.rs`, `src/gate.rs`, `src/paths.rs`, `src/tokenize.rs`. Types `RiskLevel`, `RiskFinding`, `Justification`. A command tokenizer + path/arity analysis produces a risk finding with a justification string for each shell command.
- CodeWhale `.tmp/CodeWhale` `tui/command_safety.rs` — `COMMAND_ARITY` table, per-command risk.
- hermes-agent `.tmp/hermes-agent` `tools/approval.py` — 12 HARDLINE + 47 pattern rules with rationale.

**5. EXACT REFERENCE BEHAVIOR**
jcode-command-risk tokenizes the command, classifies by arity/path/known-dangerous patterns, and returns a `RiskFinding { level, justification }`. The gate then decides allow/prompt/deny and the justification is surfaced to the caller.

**6. GAP ANALYSIS**
Nextcode has the *decision* but not the *classification + justification*. The DCG can decide but cannot explain. Porting jcode-command-risk closes this.

**7. TARGET ARCHITECTURE**
New `crates/next-code-command-risk/` crate (mirror jcode-command-risk, Rust→Rust, near COPY with crate renames). `safety.rs` / `dcg_bridge.rs` call it to enrich every `BridgeDecision` with a `RiskFinding`. `face_permission.rs` renders the justification.

**8. DATA MODEL**
```rust
pub enum RiskLevel { Safe, Low, Medium, High, Critical }
pub struct RiskFinding { pub level: RiskLevel, pub justification: String }
```
`BridgeDecision` gains an optional `finding: Option<RiskFinding>`.

**9. STATE CHANGES**
No new persistent state. The finding is ephemeral (attached to the decision rendered to the user).

**10. EVENT FLOW**
`request_permission` → `classify_for_session` → command-risk `assess(cmd)` → `RiskFinding` → decision → ServerEvent carries the finding → Face renders it.

**11. UI SPEC**
The permission card shows the command, the RiskLevel badge (color-coded), and the justification line (e.g. "writes to /etc — destructive").

**12. UX SPEC**
No new keystrokes. The justification appears inline on the permission card; keyboard users Tab through it; it is copyable.

**13. DX / CLI SPEC**
A debug flag `--permission-explain` or `NEXT_CODE_PERMISSION_EXPLAIN=1` prints the finding for each decision. `next-code doctor` can report command-risk rule coverage.

**14. KEYBINDING SPEC** — none new.

**15. ERROR MESSAGES**
"Permission denied: <justification>". Auto-deny reasons must be human-readable.

**16. EDGE CASES**
Empty command; `sudo`/`su`; pipelines with one dangerous element; shell metacharacters; Windows vs POSIX paths; unicode; long commands (truncate justification); commands the classifier cannot tokenize (fall back to a conservative RiskLevel).

**17. COMPATIBILITY RULES**
Do not change the allow/deny *outcome* (DCG stays authoritative); only add the finding. `AUTO_ALLOWED` entries stay auto-allowed (RiskLevel Safe + justification "built-in allowlist").

**18. FILES TO MODIFY**
`crates/next-code-base/src/safety.rs`, `crates/next-code-app-core/src/dcg_bridge.rs`, `src/face_permission.rs`, `Cargo.toml` (workspace member + dep).

**19. FILES TO CREATE**

**20. EXACT SOURCE REFERENCES**

### 10.2 NX-UX-004 — Multi-tier compaction (proactive / semantic / preemptive)

**STATUS**
- Current: PARTIAL · Priority: P0 · Category: Logic / UX / DX
- Strategy: PORT · Best source: jcode `compaction-core` (Reactive/Proactive/Semantic) + claude-code `src/services/compact/`
- Nextcode target files: `crates/next-code-app-core/src/agent/compaction.rs`

**1. WHY**
Today nextcode only compacts reactively when the context limit is hit (with retries). Long agentic sessions degrade before the limit: the model loses the thread, and the single reactive compact is disruptive. Proactive (compact at a threshold), semantic (embedding-similarity pruning), and preemptive tiers keep sessions productive and reduce mid-run context-limit failures — the biggest daily-pain gap for long sessions.

**2. CURRENT NEXTCODE BEHAVIOR**
`agent/compaction.rs` implements context-limit auto-compaction with 5 retries (`try_auto_compact_after_context_limit:116`), oversized-payload recovery (`try_recover_after_payload_too_large:202`), OpenAI native compaction recovery (`:254`), usage-from-stream tracking (`:313`), and an embedding snapshot for semantic compaction (`push_embedding_snapshot_if_semantic:337`). No proactive/preemptive tier exists.

**3. EXACT CURRENT CODE PATH**
`compaction.rs` fns: `note_compaction_applied:4`, `request_manual_compaction:34`, `try_auto_compact_after_context_limit:116`, `try_recover_after_payload_too_large:202`, `try_recover_oversized_openai_native_compaction:254`, `update_compaction_usage_from_stream:313`, `push_embedding_snapshot_if_semantic:337`, `fire_compaction_hook:356`.

**4. REFERENCE IMPLEMENTATION**
- jcode `compaction-core` (`.tmp/jcode`, commit `659b8cc155`): Reactive/Proactive/Semantic compaction modes. This is nextcode-core's upstream — direct copy with crate renames.
- claude-code `src/services/compact/` (`.tmp/claude-code`): 3-tier compaction + micro-compact.

**5. EXACT REFERENCE BEHAVIOR**
jcode compaction-core exposes a mode enum (Reactive = on limit; Proactive = at a configured threshold before the limit; Semantic = prune low-value context via embeddings) with a shared manager that picks the mode by context state. claude-code adds micro-compact (compact just the tail).

**6. GAP ANALYSIS**
Nextcode has the reactive core + an embedding snapshot hook but no mode dispatch. Porting jcode's mode enum + manager into `compaction.rs` gives proactive/semantic/preemptive behavior.

**7. TARGET ARCHITECTURE**
`compaction.rs` gains a `CompactionMode { Reactive, Proactive, Semantic }` and a `pick_mode(context_usage, config)` dispatcher. `push_embedding_snapshot_if_semantic` becomes the Semantic tier's input.

**8. DATA MODEL**
```rust
pub enum CompactionMode { Reactive, Proactive, Semantic }
pub struct CompactionPolicy { pub mode: CompactionMode, pub proactive_ratio: f32 /* e.g. 0.85 */ }
```

**9. STATE CHANGES**
`CompactionPolicy` on the agent; a "last proactive compact at token N" cursor.

**10. EVENT FLOW**
Usage update (`update_compaction_usage_from_stream`) → if usage ≥ proactive_ratio × limit and no recent proactive compact → `request_manual_compaction` path (Proactive). On context-limit error → Reactive (existing). Embedding snapshots → Semantic.

**11. UI SPEC**
A statusline/token-banner hint when a proactive compact is scheduled ("compacting at 85% to preserve context"). The existing compaction event / notice channels carry it.

**12. UX SPEC**
No new keystrokes. The model is compacted proactively so sessions survive longer without a mid-turn limit failure.

**13. DX / CLI SPEC**
Config keys: `compaction_mode` (`reactive`|`proactive`|`semantic`, default `reactive`), `compaction_proactive_ratio` (default `0.85`). Env `NEXT_CODE_COMPACTION_MODE`.

**14. KEYBINDING SPEC** — none new.

**15. ERROR MESSAGES**
Keep existing compaction notices; add "proactive compaction applied at N%".

**16. EDGE CASES**
Semantic mode with no embedding model (fall back to Reactive); proactive firing repeatedly (cooldown cursor); compacting a tiny session; concurrent compact + user interrupt; persisted session resumed mid-compaction.

**17. COMPATIBILITY RULES**
Reactive path stays the default and must behave byte-identically. New modes are opt-in via config.

**18. FILES TO MODIFY**
`crates/next-code-app-core/src/agent/compaction.rs`, `crates/next-code-config-types` (config keys), `crates/next-code-base/src/config*`.

**19. FILES TO CREATE**
None (mode dispatch inside compaction.rs); optionally a `next-code-compaction-core` crate if a clean split is desired (mirror jcode).

**20. EXACT SOURCE REFERENCES**
- jcode: `crates/jcode-compaction-core/` (commit `659b8cc155`) — mode enum + manager.
- claude-code: `src/services/compact/` (3-tier + micro-compact).
- nextcode: `crates/next-code-app-core/src/agent/compaction.rs`.

**21. IMPLEMENTATION STEPS**
1. Port the mode enum + manager from jcode compaction-core into `compaction.rs`.
2. Wire `update_compaction_usage_from_stream` to the proactive threshold.
3. Gate Semantic behind config + embedding availability (reuse `push_embedding_snapshot_if_semantic`).
4. Add config keys + env.

**22. TEST MATRIX**
- Unit: mode pick (reactive/proactive/semantic at thresholds); cooldown; fallback without embeddings.
- State: usage crosses threshold → proactive compact fires once.
- CLI: `NEXT_CODE_COMPACTION_MODE=proactive` honored.
- Real-world: long session stays productive past the old limit.

**23. MANUAL REAL-WORLD TEST**

**24. REGRESSION TEST**

- [ ] Config + env honored.
- [ ] Tests pass.

**16. EDGE CASES**

**17. COMPATIBILITY RULES**
